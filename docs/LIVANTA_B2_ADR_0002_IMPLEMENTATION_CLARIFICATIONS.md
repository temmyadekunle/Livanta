## 0. Purpose, precedence and non-goals

ADR 0002 records decisions D1–D7 at policy level. Five implementation questions were
left open, and B2.3/B2.4 cannot be built safely until they are answered:

1. How partial adoption is retried without weakening D2 (`destination-not-empty`).
2. How exactly one account wins the anonymous-data claim under concurrency, and what
   happens if exclusivity cannot be established.
3. Where the line sits between a disposable demo and deliberate sample-data insertion.
4. What authority, if any, B2.4 has to activate production sync.
5. How identity transitions and reminder operations are serialised across tabs without
   treating an advisory lease as a lock.

**Precedence.** This addendum refines implementation detail only. It does not change
D1–D7, does not relax any constraint in ADR 0002, and does not authorise any stage.
Where this document is more specific than ADR 0002 §6.2, §6.3 or §7.1, this document
governs for B2.3 and B2.4. Where it is silent, ADR 0002 governs.

**Approval status.** D1–D7 are the accepted B2 policy in ADR 0002 §3; A–F are additional
product and architecture boundaries approved on 2026-11-13 and recorded in ADR 0002
§2.1. The two sets are distinct, and neither authorises implementation. This document
records consequences of A–F, but its B2.3 adoption mechanics (for example marker states,
the pre-copy `reserved` write, guarded writes and claim promotion) and its B2.4
activation detail are **draft recommendations only**. Nothing in §1–§4 is accepted merely
because A–F are approved, and no section of this document authorises B2.1, B2.2, B2.3 or
B2.4 work.

**Non-goals.** No merge/import design, no claim release UI, no source deletion, no
schema change, no sync activation, no code, tests, migrations or configuration.

## 1. D3 — Adoption retry after a partial copy (draft recommendation)

### 1.1 The conflict

ADR 0002 §6.2 says a non-empty destination yields `destination-not-empty` and no
automatic write (D2). That rule is correct for *unrelated* data. It cannot also mean
"no retry", because ADR 0002 §6.3(9) requires an interrupted copy to be retryable and
§6.3(5) forbids claiming success before verification. An interrupted adoption leaves
the destination non-empty by definition, so a planner that only checks emptiness would
make every partial adoption unrecoverable and strand the user with a mixed database.

The resolution is that emptiness is not the only admissible condition. The planner must
recognise a destination that this same account's own interrupted adoption created, and
must refuse every other non-empty destination exactly as before.

### 1.2 Adoption identity and marker lifecycle

Every adoption attempt carries an `adoptionId` (random UUID generated by the first
attempt). The destination marker already proposed in ADR 0002 §6.3(6)
(`__livanta_adoption_v1`) becomes stateful:

| Field | Meaning |
|---|---|
| `version` | Schema version of the marker record. |
| `status` | `in-progress` before verification passes; `verified` only after it passes. |
| `adoptionId` | Identifies the attempt; stable across retries. |
| `sourceKind` | `anonymous` in B2. |
| `sourceFingerprint` | Stable hash over the eligible source records: ids, timestamps and values, sorted; excludes every `__livanta_*` key. |
| `plannedCounts` | Counts per store captured at snapshot time. |
| `startedAt` | Epoch ms. |
| `verifiedAt` | Present only when `status` is `verified`. |
| `verifiedCounts` | Present only when `status` is `verified`. |

Rules:

- The marker is written with `status: in-progress` **before the first user-data write**,
  after the source snapshot and claim reservation (§2). This is what makes a later
  non-empty destination attributable to this account.
- `status: verified` is written **only after** re-reading and verifying the destination
  (ADR 0002 §6.3(5)). `in-progress` is never treated as success.
- There is no time-based transition from `in-progress` to `verified`, and no automatic
  expiry into `offer`. Time passing is not evidence of abandonment.
- The marker lives in the destination account database, so it can never be read or
  inherited by another account.
- A verified marker is terminal for copying: adoption never copies again, and data
  removed later from the destination by the user is not silently restored. It does not by
  itself prove that the claim was promoted (§2.4).

### 1.3 Planner outcomes (refines ADR 0002 §6.2)

The planner remains pure and runs only with a valid account store. It is evaluated
against a source snapshot and fingerprint computed immediately before planning (§1.4),
together with the current destination and claim state. It never classifies a state that
depends on a fingerprint that was not computed in the same attempt.

| Result | Condition | Permitted effect |
|---|---|---|
| `offer` | Source snapshot non-empty; destination contains no eligible user records; no marker; no claim or reservation held by anyone. | Explicit copy / start-fresh prompt. |
| `adoption-reserved` | A valid `reserved` claim exists for the current account with the same `adoptionId`; no destination marker; destination contains no eligible user records; the claim's `sourceFingerprint` equals the snapshot fingerprint; no foreign claim or conflicting state. | Same-account resume only, using the stored `adoptionId`: write the `in-progress` marker and copy from the verified snapshot. No second reservation is created; a `claimed` record never qualifies. |
| `adoption-in-progress` | Marker `status = in-progress`, owned by the current account; the claim record is `reserved` for this account and its `adoptionId` matches the marker's; the snapshot fingerprint equals `sourceFingerprint`; every destination record id is in the snapshot id set; every existing destination record equals its snapshot record; no reserved key present. | Resume: idempotent upserts of snapshot records only, then verify against the same snapshot. |
| `finalization-pending` | Marker `status = verified` for the current account; the matching claim record is still `reserved` for the same `adoptionId`; snapshot fingerprint matches; the destination still verifies. | Same-account finalisation only: re-read and verify, confirm claim and adoption id, then promote transactionally. No copy occurs. Adoption is not complete until promotion. Other accounts remain blocked. |
| `destination-not-empty` | Destination has eligible records and there is no attributable resumable state (`adoption-reserved` or `adoption-in-progress`) for this account. | No automatic write; D2 as before. |
| `conflict` | Marker matches this account and adoption, but a destination record has an id outside the snapshot set, or the same id with different content, or the fingerprint no longer matches. | Fail closed: no write, no deletion; user informed; no merge. |
| `already-decided` | Marker `status = verified` for this account **and** the matching claim record is `claimed` with the same `adoptionId`. No other combination qualifies. | No prompt; normal app; adoption fully complete. |
| `claimed-by-other` | Claim or reservation names another user. | No copy action; source preserved. |
| `no-source` | Anonymous database absent or the snapshot has no eligible records. | No prompt. |
| `invalid` | Corrupt marker or claim, marker without a matching claim, mismatched adoption ids, a `claimed` record with a missing, `in-progress`, mismatched or corrupt marker, an unreadable or non-reproducible snapshot, or any recoverable-state condition that cannot be established with certainty. | Fail closed; no copy, no deletion; report error. |

`destination-not-empty` is still the default for every non-empty destination that cannot
be positively attributed to this account's own interrupted adoption. Unrelated records
are therefore never overwritten, merged or deleted. In particular:

- A destination with records and no marker and no attributable reservation is
  `destination-not-empty`, even if some ids happen to overlap the source.
- A reservation without a marker is not `invalid` by itself. With no destination user
  records and a matching fingerprint it is `adoption-reserved`; with any destination
  records, or any uncertainty about ownership, fingerprint or claim state, it fails
  closed (`destination-not-empty` or `invalid`) and is not resumable.
- A verified marker is not `already-decided` while its claim is still `reserved`.
  That state is `finalization-pending` and must be finalised before completion is shown.
- The state/claim pairing is strict: `adoption-reserved`, `adoption-in-progress` and
  `finalization-pending` require a matching `reserved` claim; only `already-decided`
  requires `claimed`. A `claimed` record never authorises a copy or resume.
- A `claimed` record takes precedence over `destination-not-empty`: if its marker is
  missing, `in-progress`, mismatched or corrupt, the result is `invalid` and fails closed.
  It is never a copy path.
- A marker whose `adoptionId` does not match the claim, or whose fingerprint does not
  match the current snapshot, yields `invalid` or `conflict`, never a resume.
- A resume never deletes destination records and never writes an id absent from the
  snapshot.
- If the snapshot cannot be trusted or the source has changed, the planner fails closed
  and the attempt re-plans from a new snapshot; it never plans or copies from
  inconsistent data.

### 1.4 Executor order (refines ADR 0002 §6.3)

1. Acquire the adoption/source-guard lock (`livanta:anonymous-source-guard`) and confirm
   no identity transition is pending. This is separate from the identity/reminder lock;
   adoption never acquires the identity lock, and the two locks are never nested.
2. While holding the anonymous-source write guard (§1.6), take one consistent read-only
   snapshot of the eligible source records and compute its fingerprint. This snapshot is
   the single input to planning, copying and verification.
3. Run the planner against that snapshot, its fingerprint and the current
   destination/claim state. Continue only for `offer`, `adoption-reserved`,
   `adoption-in-progress` or `finalization-pending` for this account.
4. For `finalization-pending`, take the copy-free branch: under the §1.6 guard, re-run
   destination verification, confirm the matching `reserved` claim and `adoptionId`, then
   perform promotion (step 10) and release the lock (step 11). No reservation, marker or
   copy step runs.
5. For `offer`, atomically reserve a new claim using the `adoptionId` installed in the
   §1.6 guard. For `adoption-reserved` or `adoption-in-progress`, confirm the existing
   `reserved` claim and use its `adoptionId`; never create a second reservation. A
   `claimed` record never reaches this step.
6. Write or confirm the destination marker as `in-progress` with the adoption id and
   fingerprint. If this write fails, abort before any user-data write.
7. Copy in the fixed order `settings` (user key) → `members` → `things` → `alerts`,
   idempotently by id, skipping every `__livanta_*` key, using only the snapshot from
   step 2.
8. Verify by re-reading the destination and comparing it with the same snapshot: exact
   id sets, record equality, settings equality and counts.
9. Write `status: verified` in one transaction. Nothing before this point is success.
10. Promote the `reserved` claim to `claimed` (§2.4), only after the §1.6 guard and
    revision checks pass. This is the only point at which D3's claim exists.
11. Release the lock.

`finalization-pending` is copy-free: no new reservation, marker rewrite or record copy
occurs; only re-verification and promotion run. Adoption is complete only after step 10
commits.

If the snapshot cannot be trusted, or the source changes such that the snapshot is no
longer reproducible, the attempt fails closed, copies nothing further and re-plans from a
new snapshot. Copying and verification never mix snapshots.

If verification fails, the marker stays `in-progress`, the source and existing
destination data stay intact, and the error is reported. A retry restarts at step 1 and
is idempotent.

### 1.5 Invariants

- Adoption never deletes or clears source or destination records.
- Adoption never writes a destination id that is not in the source snapshot.
- A non-empty destination without a matching in-progress marker is never written to.
- Success exists only after a persisted `verified` marker **and** promotion of the
  reservation to `claimed`.
- A verified marker alone never establishes D3 ownership while the claim is reserved.
- Adoption holds the anonymous-source write guard (§1.6) from before the snapshot
  through promotion; failure to acquire, maintain or verify it aborts without further
  copying or claiming success.
- "Start fresh" writes only the destination decision marker, copies nothing and takes no
  claim or reservation.
- Reserved keys are excluded from fingerprints, copies, verification and counts.

### 1.6 Source stability guard (B2.3 prerequisite)

The §1.4 step 2 snapshot is consistent only for the duration of its read-only
transaction. It does not by itself stop an anonymous-scope writer from changing records
between snapshot, copy and verification, which would make the copy mixed or stale.
Stability is therefore enforced by preventing and detecting writes; it is never obtained
by taking a second record snapshot.

**Guard record.** Before taking the snapshot, or before re-verification for
`finalization-pending`, adoption installs an `adoptionId` (the existing reservation's
`adoptionId` when one exists, otherwise a new one for an `offer`) and writes
`__livanta_adoption_guard_v1` to the anonymous `settings` store in one readwrite
transaction: `{ adoptionId, userId, revision, at }`, where `revision` is the current
value of `__livanta_source_revision_v1`. The snapshot transaction reads that same
revision, so record data and revision come from one consistent view. If a guard already
exists, adoption may take it over only after acquiring the exclusive Web Lock, only for
the same `userId`, and only when either no claim reservation exists yet or the
reservation's `adoptionId` equals the guard's; it then reuses that `adoptionId`.
Otherwise it aborts.

**Guarded writes.** Every application write to anonymous user records must run in one
readwrite transaction that also reads `__livanta_adoption_guard_v1`. Adoption's own
guard, claim and marker metadata writes are exempt and never count as source mutation. If
a guard is present, the application write aborts (retryable) without mutating user
records. Every such write increments `__livanta_source_revision_v1` in the same
transaction. Because the guard and the guarded write use the same database, IndexedDB
serialises their overlapping readwrite transactions: a guarded write cannot commit while
the guard is held, and a guard cannot be installed between a guarded write's check and
its commit.

**Adoption holding.** Adoption acquires `navigator.locks.request` on
`livanta:anonymous-source-guard` in exclusive mode when available, then installs the
guard record. It holds both until promotion commits or the attempt aborts, and releases
them in a finally path. The promotion transaction deletes its guard record in the same
commit that writes `claimed`, so a completed adoption leaves no orphan guard. The guard
and revision values are adoption metadata, never user data; they are not copied,
fingerprinted or counted.

**Verification.** Immediately before writing `verified`, and again inside the promotion
transaction, adoption re-reads the guard record and revision. Both must match the values
captured at acquisition, and the promotion transaction commits `claimed` only if they do.
A mismatch means the snapshot is stale: abort, write no `verified` marker, do not
promote, leave the source intact and allow same-account retry from a fresh snapshot. This
is a metadata check, not a second record snapshot.

**Failure.** If the guard cannot be acquired, is lost, or cannot be verified, adoption
aborts before any further copy and never claims success. It removes only its own guard
record and never deletes or alters source records. The reservation remains `reserved`, so
other accounts stay blocked and the existing same-account recovery rules apply.

**Locks are never nested.** Adoption holds `livanta:anonymous-source-guard` without
acquiring `livanta:identity-and-reminders:v1`. The identity transition never acquires the
source-guard lock and never waits on it. If an identity transition becomes pending while
adoption holds the guard, adoption must abort before copying, verification or promotion;
it must not wait for the identity lock while holding the guard. The guard and revision
are metadata-only and do not substitute for the identity/reminder lock.

**Enforcement limit and prerequisite.** IndexedDB cannot prevent a writer that never
checks the guard. This mechanism is enforceable only if every anonymous-scope write is
routed through the guarded path. Before enabling adoption, B2.3 must therefore:

1. add one guarded write entry point for the anonymous scope, covering the compatibility
   wrappers, sync metadata writes and clear operations, with each user-data write using a
   transaction that spans the `settings` metadata and the target user store;
2. prove by static check and tests that no other direct anonymous write path exists;
3. require the guard for adoption and fail closed where it cannot be established.

Adoption requires Web Locks. Without it, an existing guard cannot be proven stale, so a
crash prevents automatic same-account retry; a B2.2-compliant build does not open an
account store without Web Locks, so adoption is unreachable. The localStorage lease is
removed and is not evidence that the guard is held. If points 1–3 cannot be met,
adoption remains disabled in B2.3. B2.3 implementation also remains blocked until a
dedicated B2.3 architecture review approves the planner, executor, guarded-write entry
point and verification design.

## 2. D3 — Exclusive anonymous-data claim (draft recommendation)

### 2.1 What must be exclusive

Exactly one account may become the claimant of the anonymous dataset on a device
(ADR 0002 D3). Concurrency can arise from two tabs of the same account, two accounts in
different tabs, or repeated attempts after a crash. The exclusive object is the claim
record, not the source records: the source is never locked against reading, never
mutated as user data, and never deleted.

### 2.2 Claim record and states

The existing key `__livanta_sync_data_owner` (`lib/sync/meta.ts:31`) holds a versioned
record:

| Field | Meaning |
|---|---|
| `version` | `2` for the stateful record. |
| `status` | `reserved` (attempt in progress, not a D3 claim) or `claimed` (verified). |
| `userId` | Lower-case, validated Supabase UUID of the attempting account. |
| `adoptionId` | Matches the destination marker. |
| `sourceFingerprint` | Fingerprint captured at reservation time. |
| `at` | Epoch ms of the last transition. |

Reading rules:

- A legacy plain-string value is interpreted as `{ status: "claimed", userId: value }`.
  It is never overwritten by a reservation for a different account.
- Any unparseable or inconsistent value is `invalid`: fail closed.

**One parser, two consumers.** Adoption and sync ownership must read
`__livanta_sync_data_owner` through exactly the same parser and produce the same
interpretation. There is no second, weaker parser for sync. A legacy plain string is
`claimed` for its named user; a `reserved` record is adoption metadata and never
authorises sync; a malformed or inconsistent record is `invalid` for both. This document
does not implement the parser; implementing it is a B2.3/B2.4 task with tests covering
the legacy string, v2 `reserved`, v2 `claimed`, foreign user and malformed cases.

Only `status: "claimed"` satisfies D3's claim. A `reserved` record is **not** a claim and
does not authorise sync. It is adoption metadata, not user data. The single pre-copy
metadata write below is a **B2.3 draft recommendation**, not an approved permission; it
keeps ADR 0002 §6.3(7)'s rule that the *claim* is written only after verification. No
other write to the anonymous database occurs.

### 2.3 Atomic reservation and promotion

Both transitions run as a single readwrite IndexedDB transaction on the anonymous
`settings` store: read current value, evaluate, write new value, commit. IndexedDB
serialises readwrite transactions whose scope overlaps, across connections and tabs, so
check-and-set is atomic. The decision is based on what the transaction read, never on a
prior non-transactional read.

The transaction is used only to reserve a new claim, confirm an existing `reserved`
claim, or promote `reserved` to `claimed`. It never resumes from a `claimed` record.

Reservation outcomes:

| Current record | Attempt outcome |
|---|---|
| Absent (planner `offer`) | Write `reserved` for this user using the `adoptionId` installed in the §1.6 guard. Proceed. |
| `reserved`, same user, same `adoptionId` (planner `adoption-reserved` or `adoption-in-progress`) | Confirm and reuse the stored `adoptionId`; never write a second reservation. |
| `reserved`, same user, different `adoptionId` | Inconsistent state: fail closed with `invalid`. Do not reuse, overwrite or create another reservation. |
| `claimed`, same user | No reservation action. Completion is valid only when the planner established `already-decided` (verified matching marker); any attempt to reserve or copy against a `claimed` record otherwise fails closed with `invalid`. |
| Any record for another user | Fail closed with `claimed-by-other`. |
| Malformed record | Fail closed with `invalid`. |

`finalization-pending` does not appear in this table as a confirmation outcome. It
bypasses reservation confirmation and copying and proceeds directly to re-verification
and promotion. The promotion transaction itself re-reads the claim record, requires it to
be `reserved` for the same user and `adoptionId`, and commits `claimed` only if that still
holds; otherwise it fails closed.

Promotion to `claimed` is a second transaction that re-reads the record and commits only
if it is still `reserved` for the same user and `adoptionId`. A concurrent writer that
changed it wins; the loser fails closed and reports the conflict. Once `claimed`, the
record is terminal: no later attempt may copy, overwrite or resume from it, regardless of
destination contents.

### 2.4 Interruption windows

Ordering is: acquire guard → snapshot → plan → reserve/confirm → marker `in-progress` →
copy → verify → marker `verified` → claim `claimed`. `finalization-pending` skips copy
and runs guard → re-verify → promote. Because destination and claim live in different
databases, there is no cross-database transaction; recovery is by ordered, idempotent
replay.

| Crash point | Same account on retry | Another account |
|---|---|---|
| Before reservation (guard may exist, no claim) | Re-acquire the guard under the §1.6 takeover rule, take a fresh snapshot and re-plan; `offer` if destination still empty. | Same. |
| After reservation, before marker | Planner is `adoption-reserved` (matching `reserved` claim): resume with the stored `adoptionId`; write marker, copy; no second reservation. | Fail closed; source preserved. |
| After marker `in-progress`, mid-copy | Planner is `adoption-in-progress` (matching `reserved` claim): confirm subset/equality, continue idempotent upserts, verify. | Fail closed. |
| After verification, before marker `verified` | Re-run verification, then write `verified`. | Fail closed. |
| After marker `verified`, before claim promotion | Planner is `finalization-pending` (matching `reserved` claim): re-read and verify the destination, confirm the claim and `adoptionId`, then promote transactionally. Complete only after promotion commits. | Fail closed; remains blocked by the `reserved` claim. |
| After claim promotion, before lock release | Planner must return `already-decided` (verified marker plus matching `claimed` record). A missing, `in-progress`, mismatched or corrupt marker is `invalid`; no copy occurs. | Fail closed. |

No claim is ever promoted without a durable `verified` marker, and no marker is ever
marked `verified` without re-running verification. A `verified` marker with a still
`reserved` claim is `finalization-pending`, never `already-decided`. Conversely, a
`claimed` record is never an ordinary resume outcome: it is complete only as
`already-decided`, and any other marker state fails closed as `invalid`.

### 2.5 Locks are not the guarantee

- `navigator.locks.request("livanta:identity-and-reminders:v1", { mode: "exclusive" }, ...)`
  is the only hard serialiser for identity transitions, account activation and reminder
  operations (ADR 0002 D5). Adoption's `livanta:anonymous-source-guard` lock is separate.
  The two locks are **never nested**: adoption does not acquire the identity lock, and
  the identity transition neither acquires nor waits on the source guard. Adoption aborts
  if an identity transition is pending.
- The localStorage lease is removed from the design. A read-modify-write value in
  localStorage has no atomic compare-and-set; two tabs can both observe an absent or
  expired value and both proceed. It is not used for adoption, identity transitions,
  activation or reminders.
- Adoption correctness rests on the atomic claim/guard transactions, not on a lease. In
  a B2.2 build, Web Locks is present before an account store can open; if it is absent,
  the app fails closed and adoption is unreachable.
- If Web Locks is present but the atomic transaction cannot be used or its outcome is
  uncertain, adoption fails closed: no copy, no success marker, no claim, no deletion.
- An identity transition pending for a different owner aborts adoption; adoption
  re-plans only after the account is stable.

### 2.6 Failure and recovery policy

- Exclusivity failure always fails closed. The source is always preserved.
- A reservation abandoned by its owner blocks other accounts indefinitely. Releasing or
  expiring it is a separate, explicit user action outside B2; it is never automatic and
  never inferred from elapsed time.
- The planner reports `claimed-by-other` for a foreign reservation, `invalid` for a
  marker without a matching reservation or any ambiguous/corrupt state, `adoption-reserved`
  for a valid same-account reservation with no marker, no destination user records and a
  matching fingerprint, and `finalization-pending` for a verified marker whose matching
  reservation is still `reserved`.
- A reservation without a marker is resumable only under the exact `adoption-reserved`
  conditions. If the destination holds records or any ownership, fingerprint or claim
  condition is uncertain, it fails closed and is never treated as resumable.
- Only the same account may resume with the existing `adoptionId`; a second reservation
  is never created and another account is never allowed to proceed.
- Reserved keys, including the claim, are never copied, fingerprinted or counted as user
  data.

### 2.7 Identity transition and reminder barrier (D5)

ADR 0002 D5, §5.2 and §5.3 are normative, and these are **B2.2 responsibilities**. B2.1
owns only the render-time owner guard, the nullable desk input, the keyed account subtree
and the store/surface contract (§3.6); it does not implement the transition controller,
the lock or reminder coordination. B2.1 may open an account-scoped database without
requiring Web Locks, BroadcastChannel or storage-event transport, `crypto.subtle` or
cancellation-before-activation, and it must not implement or simulate those mechanisms.
An auth-enabled B2.1 build is internal-only and must not be released externally until
B2.2 has passed its acceptance criteria. This is an explicit stage boundary, not an
accidental deviation from D5. B2.2 must preserve all of the following, and every item in
this list is effective from B2.2, not B2.1:

1. One exclusive Web Lock (`livanta:identity-and-reminders:v1`) serialises identity
   transitions, account activation, native cancellation/scheduling and in-session
   notification delivery. Acquisition is bounded; `ifAvailable`/`steal` are forbidden.
2. No localStorage lease is used in any decision or scheduling path. It cannot provide
   mutual exclusion because it has no atomic compare-and-set.
3. At least one of BroadcastChannel or storage events must be available before an account
   store opens. Otherwise the build fails closed.
4. On an identity signal, the tab sets `hiding` synchronously before any await. B is not
   activated until unconditional cancellation has succeeded and the marker is `active`
   for B.
5. Only the lock holder for the current epoch/`tid` advances the marker and calls the
   cancellation primitive, through the coordinator. A tab that observes `active` for the
   target adopts it without a second cancellation. This is one cancellation authority,
   not an exactly-once guarantee: the holder may cancel again after the native call if
   the epoch or `tid` changed, and failed attempts are retried idempotently.
6. The reminder owner marker is `livanta.reminder-owner.v2` with a device-salted,
   domain-separated hash and `{ v: 2, phase, owner, epoch, tid, at }`. `tid` is an opaque
   random transition identifier paired with the epoch; it is not a user identifier. The
   marker contains no user id, email, name, token or record data.
7. Every reminder side effect re-validates the session under the lock. A stale A plan
   cannot schedule or notify after B is active. **Reconciliation** means full
   cancellation followed by a full reschedule of the target owner's complete plan,
   through the coordinator, under the lock and ownership checks; it is never a
   differential add/remove.
8. Missing Web Locks, `crypto.subtle`, transport or a failed cancellation is fail-closed:
   no account store, no native reminders, retry/reload surface.
9. Cold start uses the same coordinator path. It may not call `cancelAll` or `schedule`
   directly; owner, session and `tid` checks still apply before any cancellation or
   reschedule. A matching `active` marker may skip the transition cancellation only
   after those checks, and its plan is then scheduled in full through the coordinator.

## 3. D4 — Demo versus sample data

### 3.1 Definitions

**Disposable demo environment** — a temporary experience for exploring the product
without a session. It uses a dedicated store that is not `lifedesk`, not
`lifedesk:user:<uuid>`, not an account scope, never synced, never adopted, never
exported, cleared on exit, visibly labelled, and unreachable in any `auth.enabled`
build, including while signed out. It may exist only in a development build with
`auth.enabled === false`; any other demo requires its own separate approval. It is not
implemented in B2.

**Sample-data insertion** — a deliberate user action inside a signed-in account that
inserts example records into that account's own scoped store. It persists, is visible in
the ordinary app, is deletable by the user, and is treated as the user's data.

**Introduction completion marker** — `livanta.intro.v1`, a device-level non-secret
`localStorage` key that records only that the presentation-only introduction was
completed. It contains no personal information, is not account data, is never copied into
an account database and is never adopted in B2.3. The device-level language preference is
a separate key.

### 3.2 Prohibited

- Any demo entry point on any surface of an `auth.enabled` build, whether or not a
  session is active, including onboarding, sign-in completion, recovery, the signed-out
  welcome and the app shell. There is no production guest or demo bypass.
- Writing demo or sample fixtures into an account store as part of onboarding, sign-in,
  auth events or background work.
- Running any demo against the anonymous scope while a session exists, including the
  current onboarding path that calls `completeOnboarding` and `loadSampleData` while
  signed in.
- Demo data entering adoption, sync, exports or backups.
- Describing sample data as a demo, or presenting an account store as disposable.
- Writing personal information into the device-level `livanta.intro.v1` marker.
- Copying `livanta.intro.v1` or the language preference into an account database, or
  treating either as account data or as adoption input.

### 3.3 Permitted

- Profile's "load sample data" action, explicitly invoked by the signed-in user, writing
  through the current account-scoped `LocalStore` only.
- Deleting that sample data through the ordinary data controls.
- The legacy anonymous path in an auth-disabled development build, documented as
  dev-only (ADR 0002 D4).

### 3.4 Stage requirement

B2.1 keeps the signed-in demo entry point removed. Removing the entry point is not
sufficient on its own: the handlers it called must not be reachable from any signed-in
surface, and onboarding/sign-in completion must write only through the resolved account
store. A disposable demo may be proposed in a future design, but only with the isolation
properties in §3.1 and its own review.

### 3.5 B2.1 journey and setup boundary (approved 2026-11-13)

This boundary is approved, but approving it does not authorise B2.1 implementation.
When B2.1 is authorised, it must follow this sequence:

1. A first-time signed-out user sees presentation-only introduction screens.
2. The introduction does not create an anonymous account, open `lifedesk`, open an
   account store, read or write personal records, settings or onboarding data, or seed
   sample data. It may retain only a device-level language preference and the device-level
   completion marker `livanta.intro.v1`; both are separate `localStorage` keys and neither
   is account data. The marker records only completion, contains no personal information,
   and is never copied into an account database or adopted in B2.3.
3. After the introduction — or on a later launch when `livanta.intro.v1` is present — the
   authentication welcome screen offers Create an Account or Log In. Clearing browser or
   device storage may make the introduction appear again. There is no guest, demo bypass
   or anonymous production account.
4. A first registration that requires email confirmation shows the pending-confirmation
   state on the authentication gate. It is not a dashboard and opens no store.
5. A recovery link opens the recovery surface, which wins over signed-in and over
   `app`/`setup` even with a valid user id; it renders no account records and creates or
   hydrates no store.
6. Signing out, an expired or invalidated session (`SIGNED_OUT`) and an unresolved
   session all return to the authentication welcome and create or open no store.
7. After authentication, a new account may receive account-specific setup. Setup writes
   only the account store, and a store exists only on the `app` and `setup` surfaces
   (§3.6). Optional categories and first-record creation may be skipped; skipping still
   persists `onboarded: true`.
8. Notification permission is not a setup completion requirement.
9. Existing account records are not an empty account. Setup must not overwrite them,
   create duplicate starter records, or ignore them with an empty-state flow.
10. The setup completion marker is written only after the required setup writes succeed,
    in an idempotent sequence. The marker is never written before those writes commit.
11. Returning authenticated users with completed setup go to the dashboard. Signed-out
    users never do.
12. B2.1 does not read, migrate, delete, claim or adopt `lifedesk`; B2.3 owns adoption.
13. B2.1 does not introduce a sync activation flag. Sync remains inert.
14. B2.1 may open an account store without the B2.2 runtime prerequisites (Web Locks,
    cross-tab transport, `crypto.subtle`, cancellation-before-activation) and must not
    implement or simulate the B2.2 transition barrier. An auth-enabled B2.1 build is
    internal-only until B2.2 acceptance passes (§2.7).

### 3.6 B2.1 store and surface contract (approved 2026-11-13)

This contract restates ADR 0002 §4.4 and is approved as part of the B2.1 boundary; like
§3.5, approving it does not authorise implementation. When B2.1 is authorised:

1. A dedicated `useAccountStore` hook resolves the authenticated user's normalised id and
   returns `{ store: LocalStore | null, expectedUserId: string | null }`. No component
   constructs an account store or derives an expected owner independently.
2. An account store is created only when the resolved surface is `app` or `setup`.
3. No account store is created for loading, introduction, signed-out/authentication gate,
   pending email confirmation, recovery, auth error, invalid identity or scope error. In
   each of those states both returned values are `null`.
4. `useLivanta` accepts an explicit nullable store plus `expectedUserId`. An explicit
   `null` must never select the legacy anonymous-store overload.
5. Null-store operations are idle-safe: they resolve without reading or writing IndexedDB
   and never substitute `anonymousStore`, `openDatabase()` or a free compatibility
   function.
6. A render-time owner mismatch exposes no account records and produces a recoverable
   scope-error surface.
7. Scope-error retry retries store resolution and hydration, not `getSession`.
8. Recovery takes precedence over `app`/`setup` eligibility even with a valid user id; no
   store is created or hydrated behind recovery.
9. The single-surface decision remains the only authority for auth, recovery and store
   eligibility; no component makes a competing decision.

Acceptance tests must assert, per surface, the returned `store`/`expectedUserId`, that no
IndexedDB open or read occurs for `null`, that an explicit `null` never reaches the
anonymous path, and that a mismatched store yields the scope-error surface with a retry
that does not call `getSession`.

## 4. D6 — Production sync activation authority

### 4.1 B2.4 does not authorise activation

B2.1 does **not** introduce the activation control, its flag or any network path; sync
remains inert with `store: null`. B2.4 implements the disabled-by-default activation
control, ownership/claim integration and the D7 integration test. It does **not**
authorise production sync activation, and completing B2.4 is not approval to enable it. Production sync remains disabled before,
during and after B2.4 unless §4.2 is satisfied.

### 4.2 Authority required

Production activation requires **all** of:

1. Every precondition in ADR 0002 §7.3 complete and evidenced: adoption verified, D7
   integration test executed with its result recorded, cross-account/account-switch
   tests passing against the real engine, D1 policy accepted, privacy copy updated,
   manual Android checks done.
2. A separate explicit approval or a new ADR / ADR 0002 amendment that specifically
   authorises activation.

Passing tests, merging a PR, approving B2.4 or setting a build flag are none of them
sufficient on their own. The default remains `false`; the flag is changed only as part
of the separately approved activation.

### 4.3 Test harness scope

Activation tests may run only in an isolated harness: a synthetic or disposable Supabase
client, a fixture account store, and a flag enabled for that test process or build only.
The harness must never point at production data, must not require production credentials,
and must not produce a distributable artefact with activation enabled. Tests assert that
with the flag off a valid session and matching account store still produce zero
`from`/`rpc` calls.

## 6. Residual assumptions

- Browsers implement IndexedDB readwrite transaction serialisation for overlapping
  scopes as specified. B2.3 must verify this with a two-connection test rather than
  relying on this document.
- The source dataset is not mutated by any other feature while adoption is in progress;
  if a source fingerprint changes, adoption fails closed and reports a conflict.
- No external process writes the marker, reservation or claim keys.
- Web Locks, `crypto.subtle`, and BroadcastChannel or storage events are available on
  beta targets; otherwise B2.2 fails closed.
- `LocalNotifications.cancelAll()` does not require display permission; verify on-device.
- Production builds receive usable Supabase configuration; otherwise the build fails
  (ADR §8.1). A deployed artifact is never treated as a development build.
- Android release packaging uses a fresh web build and verifies the packaged asset set
  against `out/` (ADR §8.2); `-SkipWeb` is never a release path.
